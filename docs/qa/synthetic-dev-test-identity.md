# Synthetic dev test identity migration runbook

Issue #1027 replaces the legacy authenticated QA account with one
purpose-built identity identified in evidence only as
`synthetic_dev_test_identity`. This is an operator runbook; it contains no
mailbox, password, token, account UUID, or database row from any environment.

Repository controls can be merged independently, but Issue #1027 is not
complete until the hosted verification and retirement checklist below has
been executed and sanitized evidence has been attached. Production must not
be modified.

## Identity policy

The account must satisfy every rule below:

- It exists only in the isolated development application database.
- Its mailbox or alias is receivable, controlled by the project rather than a
  person, and monitored by at least two authorized maintainers or an approved
  team mailbox owner.
- The mailbox can receive both verification and password-reset messages. A
  `.invalid` address is not acceptable for the hosted account.
- Registration data is synthetic and environment-specific. The required
  phone value must not belong to a person and must not be reused in production.
- `public.users.role = 'user'`, `status = 'active'`, and `email_verified = true`.
- It has no admin, barber, staff, moderator, or investigator capability and no
  linked personal identity.
- It is used only by the authenticated smoke and performance workflows.
- Credentials are unique, generated by a password manager, and stored only in
  the GitHub `dev` Environment. Exposure requires immediate rotation or
  revocation.

The repository's password flow uses `public.users`; it does not create a
Supabase Auth user. The backend registration endpoint must create the row so
the password is hashed and the email-verification workflow is exercised.

## Preconditions and rollback point

Before creating or rotating anything, an authorized operator must:

1. Confirm the selected mailbox is project-controlled and can receive mail.
2. Confirm the browser and backend targets are the isolated dev frontend and
   backend named in `docs/e12-03-staging-verification-report.md`.
3. Confirm the GitHub workflows both use `environment: dev` and only the
   `STAGING_TEST_EMAIL` and `STAGING_TEST_PASSWORD` Environment secrets.
4. Record, outside the repository, the current secret versions and old account
   state as a rollback point. Do not copy values into tickets, chat, shell
   history, screenshots, or evidence.
5. Keep the old account active until the new account has passed all smoke and
   performance checks.

If no suitable receivable project mailbox exists, stop. Do not substitute a
personal mailbox, a non-receivable placeholder, or a production identity.

## Create and verify the dev identity

1. Open the real isolated dev frontend and use its password registration form.
   Supply synthetic name, username, and phone values plus the project mailbox
   and a password-manager-generated password. Do not use a database insert or
   create a Supabase Auth identity.
2. Receive the dev verification message in the project mailbox and complete
   `POST /auth/verify-email` through the normal link/UI flow.
3. Start `POST /auth/password-reset/request` through the dev UI. Confirm the
   reset message arrives in the same project mailbox, complete the reset with
   a new generated password, and treat that password as the final CI value.
4. Capture the new application user UUID in a private operator worksheet. In
   the isolated dev SQL editor, substitute that UUID locally and run this
   read-only check; do not commit or attach its row output:

   ```sql
   select
       id,
       role,
       status,
       email_verified,
       email_verified_at is not null as verification_timestamp_present,
       password_hash is not null as password_configured,
       google_sub is null as no_legacy_google_link
   from public.users
   where id = '<synthetic-user-uuid>'::uuid;
   ```

   Exactly one row must report `role = 'user'`, `status = 'active'`, and all
   three boolean checks as true. Never copy `password_hash` itself.
5. Use the existing authenticated smoke `[authz-boundary]` check to prove the
   account receives 403 from `GET /admin/stats`. A role value alone is not the
   final authorization proof.
6. A separately authorized production operator must perform a read-only exact
   mailbox lookup and record only `production_match_count = 0`. Do not capture
   the mailbox, query text containing it, or row contents in committed
   evidence. If dev and production identity stores cannot be distinguished
   confidently, stop.

## Rotate the GitHub `dev` Environment secrets

Use repository **Settings → Environments → dev → Environment secrets** and
update exactly these two entries:

- `STAGING_TEST_EMAIL`
- `STAGING_TEST_PASSWORD`

Paste values from the password manager directly into the GitHub UI. Do not add
them as repository, organization, production, variable, or file values.

The GitHub CLI is also write-only for this operation when invoked without a
value argument. Run the following commands one at a time and paste only at the
hidden prompt:

```text
gh auth status
gh secret set STAGING_TEST_EMAIL --env dev
gh secret set STAGING_TEST_PASSWORD --env dev
gh secret list --env dev
```

Do not use `--body`, command-line assignment, shell variables, pipelines,
clipboard-echo commands, or debug tracing. `gh secret list --env dev` confirms
names and update times only; GitHub does not return secret values.

## Verify smoke and performance workflows

1. Dispatch **Staging smoke tests** on the branch/commit under test. With the
   CLI, use `gh workflow run staging-smoke-tests.yml --ref <branch>` and then
   `gh run watch <run-id> --exit-status`.
2. Confirm Tier A and Tier B both pass. Tier B must prove successful login,
   authenticated user contracts, invalid-token rejection, and the non-admin
   403 boundary. Its logs may name only `synthetic_dev_test_identity`; Tier B
   produces no uploaded Playwright artifact.
3. Dispatch **Dev backend performance baseline** manually with
   `gh workflow run dev-backend-performance.yml --ref <branch>`.
4. Confirm `authenticated-read` and `controlled-write` pass with the new
   credentials. The workflow is manual because controlled-write mutates only a
   run-scoped synthetic push token and cleans it up.
5. Download the verified artifact only after the sanitization step succeeds.
   Confirm `metadata.txt` contains
   `test_identity=synthetic_dev_test_identity` and contains no email, JWT,
   Authorization header, access/refresh token, password field, response body,
   or environment dump.
6. Record only workflow URLs, commit SHA, pass/fail counts, bounded scenario
   names, and sanitized metrics. Do not attach console output or screenshots
   containing mailbox or credential values.

The active workflows reject production hosts before authentication or load.
Never override those guards to diagnose a failed run.

## Inspect old-account dependencies

Do this only after the new identity passes both workflows and no active
workflow references the old secrets. Use the old application UUID, not its
mailbox, in an isolated dev SQL session. The following read-only query returns
counts only:

```sql
with target(id) as (values ('<old-user-uuid>'::uuid))
select 'games_created' as dependency, count(*) from public.games, target where created_by = target.id
union all select 'game_participation', count(*) from public.game_players, target where user_id = target.id
union all select 'fields_added', count(*) from public.fields, target where added_by = target.id
union all select 'fields_removed', count(*) from public.fields, target where removed_by = target.id
union all select 'field_reports_created', count(*) from public.field_reports, target where user_id = target.id
union all select 'field_reports_reviewed', count(*) from public.field_reports, target where reviewed_by = target.id
union all select 'notifications', count(*) from public.notifications, target where user_id = target.id
union all select 'notification_preferences', count(*) from public.notification_preferences, target where user_id = target.id
union all select 'push_tokens', count(*) from public.push_tokens, target where user_id = target.id
union all select 'moderation_target_audit', count(*) from public.user_moderation_audit, target where target_user_id = target.id
union all select 'moderation_actor_audit', count(*) from public.user_moderation_audit, target where actor_user_id = target.id
union all select 'authentication_audit', count(*) from public.authentication_audit_events, target where user_id = target.id
union all select 'verification_tokens', count(*) from public.email_verification_tokens, target where user_id = target.id
union all select 'password_reset_tokens', count(*) from public.password_reset_tokens, target where user_id = target.id
union all select 'linked_identities', count(*) from public.user_identities, target where user_id = target.id
union all select 'content_reports_created', count(*) from public.content_reports, target where reporter_user_id = target.id
union all select 'content_reports_reviewed', count(*) from public.content_reports, target where reviewed_by = target.id
union all select 'blocks_created', count(*) from public.user_blocks, target where blocker_user_id = target.id
union all select 'blocks_received', count(*) from public.user_blocks, target where blocked_user_id = target.id;
```

Also verify the deployed foreign-key actions from the catalog instead of
assuming schema parity:

```sql
select
    constraint_name,
    table_name,
    delete_rule
from information_schema.referential_constraints
join information_schema.table_constraints using (constraint_catalog, constraint_schema, constraint_name)
where unique_constraint_schema = 'public'
  and unique_constraint_name = 'users_pkey'
order by table_name, constraint_name;
```

Expected effects from the current schema are:

- `SET NULL` preserves shared fields/games, content-report references, reviewer
  references, and authentication audit rows while removing the direct user FK.
- `CASCADE` removes participation, notifications/preferences, push tokens,
  verification/reset tokens, linked identities, blocks, user-created field
  reports, and moderation rows where the account is the target.
- Security attribution evidence is pseudonymous and has no direct user FK; its
  180-day retention remains unchanged.
- Authentication audit rows are retained with `user_id = NULL` until their
  enforced 180-day cleanup window.

`user_moderation_audit` is security-relevant and target rows currently cascade.
If the dependency query finds any such row that must be retained, do not hard
delete the account. Leave it revoked and escalate for an evidence-preserving
retirement decision; this Issue does not change that schema.

## Revoke and retire the old account

Proceed only when the new identity is green, both GitHub secrets have been
rotated, dependency impact is recorded, and a rollback point exists.

1. Confirm no workflow run is using the old secret versions.
2. End any controlled old-account session through `POST /auth/logout`; this
   advances `tokens_valid_after`. Do not record its token.
3. If hard deletion is blocked by retained audit/dependency data, use the
   authenticated admin moderation route to ban the old ordinary user and keep
   it revoked. Verify an old credential login is denied, then stop retirement
   at this reversible state pending an approved scrub strategy.
4. If the dependency audit proves hard deletion is safe, use the existing
   authenticated `DELETE /auth/account` flow with the old account's reauth
   credential. That RPC atomically reconciles active game counters, revokes the
   account, and applies the deployed FK actions. Do not issue ad-hoc `DELETE`
   SQL and do not delete audit tables.
5. Verify the old credentials no longer authenticate, the old `public.users`
   row is absent, shared records were de-identified as predicted, and retained
   security evidence still exists within policy.
6. Re-run smoke Tier B after retirement and confirm production was untouched.

## Rollback

- Before old-account retirement: restore the previous `dev` Environment secret
  versions through the same write-only UI/prompt only if the old account is
  still active and uncompromised. Re-run Tier B; do not modify production.
- If the new account or mailbox fails: remove it from CI, revoke it, diagnose
  delivery in dev, and create a replacement project-controlled identity. Do
  not fall back permanently to a personal mailbox.
- After old-account hard deletion: there is no application restore path. Use a
  new synthetic identity; do not restore PII from backups merely to recover a
  QA credential.
- Revert repository hardening by reverting this Issue's commit. Secret changes
  and hosted accounts are operational state and require separate manual
  rollback.

## Evidence checklist

Attach only:

- project-mailbox ownership confirmation without the address;
- verification and password-reset receipt booleans;
- `role=user`, `status=active`, `email_verified=true`, non-admin 403, and
  production-match-count-zero booleans;
- secret names plus update timestamps, never values;
- smoke/performance run URLs, commit SHA, exact counts, and sanitized metrics;
- old dependency counts and chosen retirement outcome without account UUID;
- proof that old credentials fail and production remained untouched.

Hosted verification status remains **pending** until all of those items are
attached. Repository tests cannot prove mailbox ownership, email delivery,
GitHub secret values, hosted workflow success, or old-account retirement.
